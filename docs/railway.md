# Railway: виртуальная торговля

Проект: `crypto-trading-paper` (`2ae89da4-7cfd-41de-b840-804204967824`).
Сервис: `trading-paper` (`8834e037-eaba-4cbb-980b-f9d9a7e5cecf`).
Production: `2b66cae6-d2ca-44cd-b8c6-28f43b7fdfac`.
Постоянный диск: `3f5d30a1-89d3-4a86-b782-627f85961b23`, `/data`, Amsterdam.
Публичный домен не создавался. Журналы доступны владельцу через Railway.

`cloud_runtime.py` запускает один торговый процесс и отдельный процесс обучения.
Это только paper trading: реальные биржевые ордера не реализованы.

- `paper_runner.py` проверяет позиции примерно раз в минуту; Binance WebSocket
  непрерывно обновляет bid/ask, REST служит резервом. Это не исполнение на каждом тике биржи.
- `daily_learn.py --research-only` работает с отдельной `research.db`: четыре минуты
  бюджета эволюции каждые шесть часов. Один цикл и загрузка данных могут занять больше бюджета.
- SQLite, снимки кандидатов, журналы и локальные резервные копии находятся на volume `/data`.
- Отсутствие volume или исходного виртуального счёта останавливает запуск.
- Один экземпляр сервиса, OS-lock, отсутствие sleep и перезапуск `ALWAYS`.
- `/health` показывает состояние процесса; `/api/summary` — результаты и независимые
  фиксированные испытания. Панель `/` доступна только для чтения.
- Проверка запуска Railway дополняется watchdog: отсутствие нового снимка пять минут
  завершает процесс, чтобы Railway перезапустил его. Это не гарантирует доступность биржи.
- Копии SQLite создаются через backup API каждый час в семи суточных слотах на volume.
  Они защищают от повреждения рабочей базы, но не от потери самого volume; нужны также
  резервные копии volume средствами Railway.

На момент переноса API Railway отказал в `volumeInstanceBackupCreate` и
`volumeInstanceBackupScheduleUpdate` с `Not Authorized`. Внешние снимки volume
не настроены; работают описанные выше копии SQLite на самом volume.

## Перенос

1. Создать отдельный проект и сервис, подключить `/data`, задать `PAPER_ENABLED=false`.
2. Деплоить только Docker-контекст проекта; `.railwayignore` исключает базы, книги,
   окружения, локальные настройки и секреты. Account API token используется только CLI,
   в контейнер не передаётся.
3. Проверить `/health` в состоянии `standby`.
4. Отключить workflow `daily-learn`, дождаться завершения активного запуска. Скачать и
   проверить последний release `bot-state`; сохранить его SHA256 и сверку счёта.
5. Установить `BOOTSTRAP_SHA256` и `PAPER_ENABLED=true`, передеплоить. Первый запуск
   проверяет SHA256 архива и целостность SQLite. Существующая база никогда не заменяется.
6. Проверить баланс, историю, новые heartbeat и возобновление после перезапуска.

После переноса GitHub не должен продолжать торговые записи. Не включать старый workflow
как «резервный»: его счёт станет независимой устаревшей копией. При откате сначала
остановить Railway и экспортировать актуальную SQLite через backup API.

## Изменения модели paper-v4

Общие правила стопов, гэпов и cooldown для live paper и бэктеста. Net PnL включает
комиссии входа и выхода. Просадка и доходность учитывают издержки первого бара.
Поэтому старые golden-значения audit-v3 сознательно заменены после независимой проверки
арифметики (`test_v4.py`), а синтетические OHLC исправлены так, чтобы open лежал внутри
high/low. На тех же данных результат ряда стратегий стал хуже; это исправление учёта,
а не улучшение доходности. Старая история сохраняется отдельными когортами.

DSR и стресс издержек обязательны для основного демо-портфеля. Изолированные фиксированные
виртуальные испытания имеют собственные счета и более широкий отбор для сбора новых данных.
Их результаты не добавляются к балансу основного счёта. Смена кода прекращает прежнее
фиксированное испытание, сохраняя его журнал.

Порог готовности — только повод для ручного рассмотрения: не менее 90 дней, 100 закрытых
сделок, проверка издержек, просадки, статистической неопределённости и пропусков наблюдений.
Переход к реальным деньгам автоматически не выполняется.

## Публичная панель (по паролю)

Панель `/` и API (`/api/status`, `/api/summary`, `/api/track`) — только для чтения,
но при публичном домене их видно из интернета. Поэтому HTTP-сервер поддерживает
HTTP Basic-авторизацию:

- `DASHBOARD_PASSWORD` — если задан, все маршруты, КРОМЕ `/health`, требуют пароль
  (`/health` открыт для health-check Railway). Если пароль не задан — панель открыта,
  и при старте пишется предупреждение в лог.
- `DASHBOARD_USER` — имя пользователя, по умолчанию `owner`.

Порядок включения публичной панели:
1. В Railway задать переменную `DASHBOARD_PASSWORD` (длинный случайный пароль), передеплоить.
2. Проверить в логах, что предупреждения «panel is OPEN» больше нет.
3. Создать публичный домен сервиса в Railway.
4. Открыть домен: браузер спросит логин (`owner`) и пароль. Без пароля — 401.

Реальных ордеров нет и с публичной панелью: она только показывает виртуальный счёт.

## SSH-доступ

SSH к контейнеру включается на стороне Railway (платформенная настройка, не код).
Это дополнительный путь входа в сервер — включать только при конкретной задаче
(ручная отладка) и отключать после. Для штатной работы не нужен: рантайм сам
перезапускается по watchdog, бэкапы SQLite ежечасные, панель — для чтения.
